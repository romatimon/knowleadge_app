# Knowledge App

**Внутренняя база знаний для менеджеров по сертификации.**

Knowledge App объединяет рабочие инструкции, типовые ситуации, нормативные сведения, сроки испытаний и нормы отбора образцов в одном веб-интерфейсе. Приложение помогает менеджерам быстрее находить ответы на повседневные вопросы и работать с единым актуальным источником информации.

Проект построен на Streamlit, хранит данные в SQLite и поддерживает контейнеризованное развёртывание через Docker.

## Возможности

### Для менеджеров

- поиск по материалам базы знаний;
- просмотр типовых рабочих ситуаций, справок и правил;
- доступ к инструкциям и пошаговым алгоритмам;
- просмотр сроков проведения испытаний;
- просмотр сроков действия сертификатов и деклараций;
- информация по испытаниям аккумуляторов и батарей;
- нормы отбора образцов по группам продукции;
- фильтрация нормативных таблиц по отдельным колонкам;
- подсветка найденного текста.

### Для администратора

- отдельный вход по паролю;
- добавление, редактирование и удаление материалов FAQ;
- управление инструкциями и алгоритмами;
- редактирование нормативных таблиц;
- указание краткого описания, ключевых слов, даты обновления и источника;
- автоматическое сохранение изменений в SQLite;
- создание резервной копии базы перед изменением данных.

## Разделы базы знаний

Приложение работает с шестью группами материалов:

| Раздел | Содержание |
|---|---|
| FAQ | типовые ситуации, справочные вопросы, правила и исключения |
| Сроки испытаний | лаборатории и сроки проведения испытаний по группам продукции |
| Сроки действия документов | сертификаты и декларации для различных регламентов |
| Аккумуляторы и батареи | ограничения, сроки испытаний и количество образцов |
| Инструкции | внутренние рабочие инструкции и алгоритмы |
| Нормы отбора | количество образцов и нормативные документы по группам продукции |

## Хранение данных

Приложение использует каталог, заданный переменной `DATA_DIR`.

- при локальном запуске данные по умолчанию находятся в корне проекта;
- в Docker используется каталог `/data`;
- `knowledge.db` и каталог `backups/` сохраняются на сервере независимо от пересборки контейнера.
- перед каждым изменением создаётся проверенная резервная копия SQLite;
- приложение хранит не более десяти автоматических копий вида `knowledge_20*.db`; ручные и именованные копии не удаляются.

Файлы с корпоративными материалами исключены из Git и Docker-образа.

## Безопасность

- пароль администратора передаётся через переменную окружения;
- стандартного резервного пароля в исходном коде нет;
- если `ADMIN_PASSWORD` не настроен, административный режим отключается;
- `.env` и базы SQLite не включаются в Docker-образ;
- пользовательский текст экранируется перед отображением через HTML;
- данные администратора сравниваются безопасным методом без обычного строкового сравнения.

Приложение предназначено для внутреннего использования. Доступ к порту `8501` следует ограничивать корпоративной сетью, VPN, firewall или обратным прокси-сервером с авторизацией.

## Конфигурация

Скопируйте `.env.example` в `.env` и задайте пароль администратора:

```env
ADMIN_PASSWORD=your-strong-admin-password
IMAGE_TAG=2026.09.02-1
HOST_DATA_DIR=/home/roman/knowledge_app
```

Для локального запуска используется только `ADMIN_PASSWORD`. Переменные `IMAGE_TAG`
и `HOST_DATA_DIR` нужны при развёртывании на сервере. Файл `.env` не должен
добавляться в Git.

## Локальный запуск через Docker Compose

Клонируйте репозиторий:

```bash
git clone https://github.com/romatimon/knowleadge_app.git
cd knowleadge_app
```

Убедитесь, что в корне проекта есть `knowledge.db` и каталог `backups/`, затем
запустите проект из Git Bash:

```bash
docker compose up -d --build
```

Приложение будет доступно по адресу:

```text
http://localhost:8502
```

Посмотреть состояние и журналы:

```bash
docker compose ps
docker compose logs -f knowledge-app
```

Остановить приложение:

```bash
docker compose down
```

После изменения кода снова выполните `docker compose up -d --build`. Локальный
Compose собирает образ `knowledge-app:local` из текущих файлов и не загружает
рабочий образ с сервера.

## Локальный запуск без Docker

При необходимости приложение можно запустить непосредственно в Python:

```powershell
python -m venv .venv
.venv\Scripts\activate
pip install -r requirements.txt
$env:ADMIN_PASSWORD = "ваш-пароль"
streamlit run app.py
```

В Git Bash команда установки пароля выглядит так:

```bash
export ADMIN_PASSWORD="ваш-пароль"
streamlit run app.py
```

## Публикация проверенной версии

После локальной проверки назначьте образу отдельную версию и отправьте её в
Docker Hub. Пример для Git Bash:

```bash
VERSION=2026.09.02-1
docker tag knowledge-app:local rtimonin569/knowledge_app:$VERSION
docker login
docker push rtimonin569/knowledge_app:$VERSION
```

Для каждого выпуска задавайте новую версию. Файлы `.env`, `knowledge.db` и каталог
`backups/` исключены из контекста сборки и не попадают в образ.

## Развёртывание через Portainer

Перед первым запуском на сервере должны находиться:

```text
/home/roman/knowledge_app/knowledge.db
/home/roman/knowledge_app/backups/
```

Создайте Stack из `compose.production.yml` и добавьте переменные окружения:

```text
ADMIN_PASSWORD=<надежный пароль администратора>
IMAGE_TAG=2026.09.02-1
HOST_DATA_DIR=/home/roman/knowledge_app
```

`ADMIN_PASSWORD` хранится только в настройках Stack. Не добавляйте реальный пароль в Compose-файл, GitHub или Docker-образ.

При обновлении опубликуйте образ с новым тегом, измените `IMAGE_TAG`, затем
выполните **Pull and redeploy** в Portainer. Рабочая база и резервные копии
останутся на сервере благодаря bind mounts.

## Запуск Compose на сервере

При необходимости production-конфигурацию можно запустить без Portainer. Создайте
на сервере `.env` на основе `.env.example`, затем выполните:

```bash
docker compose -f compose.production.yml pull
docker compose -f compose.production.yml up -d
```

Посмотреть журналы:

```bash
docker compose -f compose.production.yml logs -f knowledge-app
```

Остановить приложение:

```bash
docker compose -f compose.production.yml down
```

Корпоративные данные подключаются к контейнеру отдельно. Не добавляйте базу знаний в GitHub или публичный Docker registry.

## Правила добавления материалов

Используйте FAQ для одного конкретного вопроса сотрудника, инструкцию — для
повторяющегося процесса, а справочную таблицу — для сроков, количеств и других
точных значений.

Хорошая инструкция содержит разделы:

1. Назначение.
2. Когда применять.
3. Что подготовить.
4. Алгоритм из пронумерованных действий.
5. Особые случаи.
6. Результат.

Один шаг должен описывать одно действие и начинаться с глагола: «Проверить»,
«Запросить», «Создать», «Передать». Если шаг зависит от условия, используйте
формулировку «Если …, то …». Не создавайте FAQ и инструкцию с одинаковым
содержанием: краткий FAQ должен направлять сотрудника к одной основной инструкции.
